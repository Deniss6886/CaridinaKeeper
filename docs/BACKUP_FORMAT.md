# CaridinaKeeper Backup Format

Last reviewed: 2026-09-12

This document defines the version 1 full-backup envelope and the security rules
for JSON restore and CSV export. JSON is the authoritative, lossless backup
format. CSV is intended for inspection and analysis in spreadsheet software and
is not a full restore format.

## Media type and filename

A version 1 backup is UTF-8 JSON conforming to RFC 8259.

- Recommended media type: application/json
- Recommended filename:
  caridinakeeper-backup-YYYY-MM-DDTHH-mm-ssZ.json
- The filename is generated by the application and contains no tank name, note,
  or other user-controlled text.

The file is not encrypted, authenticated, or digitally signed. Validation can
show that a file has the expected structure; it cannot prove who created it or
that no person deliberately modified it.

## Version 1 envelope

The root value must be one object with exactly these members:

    {
      "schemaVersion": 1,
      "exportedAt": "2026-09-12T10:00:00.000Z",
      "appVersion": "0.1.0",
      "data": {
        "tanks": [],
        "parameterDefinitions": [],
        "targetRanges": [],
        "waterReadings": [],
        "maintenanceEvents": [],
        "breedingLines": [],
        "breedingEvents": [],
        "crosses": [],
        "reminders": [],
        "settings": {}
      }
    }

Requirements:

- schemaVersion is the integer 1.
- exportedAt is an RFC 3339/ISO 8601 UTC timestamp with a trailing Z.
- appVersion identifies the exporting application version but does not select
  the schema. Only schemaVersion selects the parser and migration path.
- data contains every collection, including empty collections.
- settings is one validated settings object.
- Unknown root members, unknown collection names, and unknown entity members
  are rejected in version 1 unless a later schema explicitly defines them.
- JSON object member names must be unique.

The entity schemas are defined by the versioned runtime validators and the
project data-model documentation. TypeScript declarations alone are not
runtime validation.

## Common value rules

- IDs are stable, opaque, non-empty strings generated by the application.
  Version 1 uses cryptographically strong UUID-style identifiers.
- IDs are unique within their entity collection.
- References identify an existing record of the expected type.
- Dates without a time use YYYY-MM-DD.
- Instants use RFC 3339 UTC timestamps.
- Numeric values are JSON numbers and must be finite. NaN, Infinity, and
  negative Infinity are never valid JSON backup values.
- Enumerated fields accept only values defined by schema version 1.
- Required text must not become empty after its field-specific normalization.
- User text is data only. It is never interpreted as HTML, JavaScript, a URL,
  CSS, or a property path.

Referential checks include at least:

- Every water reading refers to an existing tank and parameter definition.
- Every target range refers to an existing tank and parameter definition.
- Tank-scoped maintenance events, breeding events, and reminders refer to an
  existing tank.
- Breeding-event and cross references identify existing breeding lines where
  the field is present.
- Cross parent and result relationships do not contain dangling IDs.

## Parser limits

Version 1 restore must fail closed before database mutation when any of these
limits is exceeded:

- File size: 25 MiB (26,214,400 bytes).
- JSON nesting depth: 32.
- Aggregate entity records across all collections: 250,000.
- Individual string length: 32,768 UTF-16 code units, with lower field-specific
  limits for names, units, IDs, and enumerations.

These limits are safety bounds against memory exhaustion and pathological
input. If a legitimate export approaches a limit, the application should warn
before export and a future schema or streaming format should revise the limit
deliberately rather than silently accepting unbounded input.

The file extension and browser-supplied MIME type are hints only and are not
trusted security checks.

## Secure restore algorithm

Restore is a replace operation in version 1. It is never an implicit merge.

1. The user explicitly chooses a file and confirms that a successful restore
   will replace current application records.
2. Check the byte-size limit before reading the complete file.
3. Decode as UTF-8 and reject invalid encoding according to the chosen decoder
   policy.
4. Parse strictly as JSON. Never use eval, Function, dynamic import, or an
   object deserializer that instantiates arbitrary classes.
5. Reject duplicate object member names.
6. Reject the keys **proto**, constructor, and prototype at every depth.
7. Validate the complete envelope against the exact schema selected by
   schemaVersion.
8. Reject unknown future schema versions. Never guess their meaning.
9. For a recognized older schema, migrate a detached in-memory value through
   each explicit, tested migration step.
10. Validate field constraints, collection limits, unique IDs, and all
    cross-record references after migration.
11. Map allowed fields into newly created domain objects. Do not recursively
    merge untrusted objects into defaults or existing settings.
12. Open one read-write IndexedDB/Dexie transaction covering every affected
    table. Clear and repopulate all versioned stores inside that transaction.
13. Commit only after every write succeeds. Any parse, validation, migration,
    quota, or write error aborts the transaction and preserves the previous
    database.
14. Re-read representative counts and references after commit before reporting
    success.

Validation errors should identify the failing path and a safe explanation but
must not render imported text as HTML or copy an entire potentially sensitive
backup into logs.

The implementation must test a quota failure and an exception after stores have
been cleared but before all inserts complete. Both tests must prove that the
old database survives unchanged.

## Schema evolution

- A format change increments schemaVersion.
- Application releases may change independently without changing the backup
  schema.
- Each supported old schema has a deterministic, pure migration to the next
  schema.
- A migration never writes to IndexedDB directly.
- Export always emits the newest schema supported by that application build.
- A newer, unknown schema is rejected with a non-destructive message.
- Deprecated schema support and its removal are recorded in CHANGELOG.md.

## CSV water-reading export

CSV is exported using a fixed, documented column order:

| Column        | Meaning                                |
| ------------- | -------------------------------------- |
| tankId        | Stable tank identifier                 |
| tankName      | Display name at export time            |
| parameterId   | Stable parameter-definition identifier |
| parameterName | Display name at export time            |
| value         | Validated finite numeric value         |
| unit          | Validated unit                         |
| measuredAt    | RFC 3339 timestamp                     |
| note          | Optional user text                     |

CSV requirements:

- UTF-8 encoding.
- MIME type text/csv;charset=utf-8.
- One header row and CRLF row endings.
- Every field is enclosed in double quotes.
- A double quote inside a field is represented by two double quotes.
- Numeric fields come only from validated numbers and use a period as the
  decimal separator in the machine-readable file.
- Newlines in text remain inside a correctly quoted field.
- The generated filename contains no user-controlled text.

### Spreadsheet formula injection

Spreadsheet applications can interpret text beginning with formula characters
as executable formulas. Quoting alone is not a reliable defense.

For the spreadsheet-oriented CSV, each user-controlled text cell is inspected
before RFC 4180 quoting. If its first significant character, including after
leading whitespace or a line break, is an equals sign, plus sign, minus sign,
at sign, tab, carriage return, line feed, or a known full-width equivalent, the
exporter prefixes a tab character inside the quoted field. This is an
Excel-oriented mitigation and the tab becomes part of the CSV data.

There is no universal mitigation that is simultaneously safe in every
spreadsheet program and lossless for every downstream parser. Consequently:

- JSON remains the lossless backup.
- CSV is labelled as spreadsheet-safe, not round-trip-safe.
- Users are warned before opening untrusted exports in spreadsheet software.
- Tests cover delimiter, quote, embedded-newline, formula-prefix, leading
  whitespace, and full-width-character cases.

Version 1 does not use CSV for full restore. If row import is added later, it
must use a maintained CSV parser, exact header allowlisting, duplicate-header
rejection, row/column/size limits, per-cell schema validation, and the same
transactional write guarantees. Splitting a row on commas is not a CSV parser.

## Privacy and handling

Backups can contain free-text notes, purchase information, and complete
husbandry history. The application does not upload them, but downloaded files
are outside browser storage controls. Users should store, share, and delete
them according to their sensitivity. Deleting local application data does not
delete previously downloaded backups.
